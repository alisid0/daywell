# Recorded replies and new AI responses

Owner request, 9 October 2026: connect food understanding and let Daywell quickly choose between an existing recording and a newly generated response across the app. This implementation follows the two-stage JEV idea in [PR #35](https://github.com/alisid0/daywell/pull/35), using its synthetic test phrases from `1fc70e2`.

## What happens to a request

1. The shared Daywell host applies the existing wellness boundary and recognises everyday commands on the device. Commands keep their existing review, confirmation and undo behaviour.
2. Food statements such as “I have four eggs and noodles”, consumed meals and planning requests open the corresponding capture review with the words preserved. Nothing is saved automatically. OpenAI interprets food only after the person requests understanding.
3. For other requests, an exact authored prompt can select its current, playable recording locally. The transcript and Listen/Stop playback controls remain available. Missing, outdated, external, clinical, tool or live-only clips cannot be selected.
4. If there is no exact match, the optional server-side JEV picker selects a topic, then an approved reply within it. Both stages include `none_fit`. A choice must have confidence at least 0.85, a valid complete probability distribution and a clear lead over the next choice. Provider text never becomes the response; only the approved local ID and authored transcript can be returned.
5. If no reply fits, confidence is low, the connection fails or the 1.8-second picker budget expires, offer a new ElevenLabs conversation. Preserve the original request and send it once the conversation connects. Failed connections keep the request for retry. Explain the provider sharing before the person starts.

JEV is a classifier, not a response generator. It does not estimate calories, write new scripts or execute actions. Food quantities, nutrients, personal facts and task requests bypass generic clip selection. New conversations are never automatically published into the shared recording library.

The shared host is mounted across Today, Eat, Move, Sleep, Relax and Calendar. Workout step commands and cues continue through their specific local routine controller. Food-photo analysis and live ElevenLabs conversations retain their own paths. **Once a person explicitly starts continuous live conversation, subsequent turns are generated by ElevenLabs, not intercepted by this picker.** Routing every live audio turn would require a separate streaming speech/transcript and playback architecture; this checkpoint does not claim that integration.

## Connections and activation

Use the masked forms at the local `/voice-setup` page. Keys are saved only in ignored `.dev.vars`, never returned in API responses, browser bundles or logs. Restart the local preview after changing them. Local saving does not configure the hosted Worker or validate account credit/model access.

- `OPENAI_API_KEY`: food photos, recorded descriptions and meal proposals. Existing defaults are `gpt-4.1-mini` for structured responses and `gpt-transcribe` for recorded speech; overrides remain available.
- `ELEVENLABS_API_KEY` and `ELEVENLABS_AGENT_ID`: new text/live-voice responses through the existing authenticated agent.
- `TYPESAFE_API_KEY`: optional JEV classification.
- `TYPESAFE_PICKER_ENABLED=true`: an explicit activation gate, **left unset/false until the real-provider acceptance checks below pass**. A key alone never enables an untested classifier.

For the private Worker, follow [Cloudflare hosting](cloudflare-hosting.md): rebuild with the real ignored profile after any ordinary or synthetic build; verify the Worker/account/database before secret prompts or deployment. Store provider keys as Worker secrets. The enable marker can also be a Worker secret so it survives the strict hosting profile without putting secrets in generated configuration. Do not use the synthetic `cloudflare:check` output for deployment. A source push does not update the phone app.

At this checkpoint neither OpenAI nor TypeSafe was detected in the active local setup, and the hosted connection page still showed food understanding awaiting setup. The owner reported saving OpenAI; a follow-up asks for the masked form's status message, not the key. Food AI and real JEV activation therefore remain unverified. This new request supersedes the earlier choice to leave food AI disconnected once the key is actually available.

## Data and costs

Before broader matching, the person can agree to send unmatched requests and the current area to TypeSafe for this visit. Only those words and the area are sent as user context. The picker has no access to saved journal entries, body profile, account ID or other users' records. It also receives the public authored choice catalogue. There is no personal-response cache or raw request logging.

[TypeSafe's privacy policy](https://typesafe.ai/legal/privacy-policy) states that API inputs are not used to train/fine-tune models. It describes US hosting and retention as reasonably necessary rather than a fixed short TTL. The app links that policy; do not promise zero retention. Review processor terms and transfer arrangements before public launch.

Exact recordings and local commands do not consume an API allowance. Each dispatched JEV request counts separately, up to 120 per person per UTC day; two stages can therefore use two requests. Food transcription and interpretation each count against the existing 20 OpenAI requests per day. Validate the complete input before reserving usage; refund explicit provider refusals and cancellation before dispatch. A lost response after dispatch is conservatively counted because billing is unknown. See [usage limits](usage-limits.md).

## Verification and remaining gates

Default local benchmark (no external calls):

```sh
node scripts/check-response-router.mjs
```

The initial Windows measurement used 1,281 eligible clips and 1,860 decisions: local p50 0.714 ms, p95 0.899 ms, max 2.915 ms. This is warm local JavaScript decision time only. It excludes microphone capture/transcription, initial asset loading, network round trips, JEV and ElevenLabs. It is not a phone or generated-response latency promise.

After a private JEV key is available, explicitly run the paid benchmark against the production router:

```sh
node --env-file=.dev.vars scripts/check-response-router.mjs --jev
```

It uses synthetic PR #35 phrases only, sends at most two classification requests per phrase, writes ignored results under `work/jev-picker/` and never enables the feature. Review the results before enabling. The original proposal's minimums are 80% correct matchable phrases, 80% correct no-fit handling and at most three wrong high-confidence recordings. Also inspect individual reply suitability, personal-food bypasses, safety examples and real-phone p95 latency (target under one second; 1.8-second timeout is the failure ceiling). Some legacy “matchable” phrases now intentionally take local-command or fresh-food paths; review these explicitly rather than silently changing the score to pass. A numerical pass alone is insufficient.

Unit tests cover both stages, missing/stale recordings, malformed confidence/probabilities, no-fit, cancellation, local boundaries/commands, quota isolation/refunds and complete capture validation. `scripts/smoke-response-router.mjs http://localhost:5192` adds read-only auth/origin/body-limit and routing checks against an isolated local preview. Physical microphones, generated speech quality, first-audio latency, live seed-message delivery, real food photo accuracy and TypeSafe accuracy remain provider/device acceptance gates.

API references: [TypeSafe system-one API](https://docs.typesafe.ai/api), [OpenAI structured outputs](https://developers.openai.com/api/docs/guides/structured-outputs), [OpenAI transcription](https://developers.openai.com/api/docs/guides/speech-to-text).
